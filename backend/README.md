# Local multi-journal workflow (development only)

This separate Django application is an early backend for testing the publishing workflow with entirely fictional data. It does not serve or modify the static prototype in `dist/` and is not deployed to SCIENTARA. It must not be used for real manuscripts or exposed to the public internet.

## What works locally

- An organisation can contain multiple journals. Test users can have author, editor, reviewer, editorial coordinator, production editor, journal site manager or journal AI manager roles in individual journals; the same user may have multiple roles.
- An author with a journal role can create a draft with a PDF, then explicitly submit it. Editors cannot see drafts or perform editorial actions on their own submissions.
- A journal coordinator assigns specific eligible editors after submission. The coordinator can see submission titles and assignment history, but receives no manuscript, abstract or confidential-review access solely from that role. Editors can access only assigned submissions while their journal role and assignment remain active. A coordinator cannot manage their own submission or one they reviewed or recused from; an author, invited reviewer or the coordinator making the assignment cannot be assigned as editor. A coordinator who is also an editor requires another eligible coordinator to assign them. Editors may recuse themselves, immediately ending their access and requiring a coordinator to arrange another editor. The assignment and recusal history is retained; an earlier decision is not automatically reversed. These checks do not establish the absence of other conflicts.
- Journals can use a standard review file or require a separate reviewer PDF; newly created journals default to the separate-file policy. The policy is captured when a submission is created. In separate-file mode, the author uploads and confirms a reviewer file for every version, and an authorised editor must manually inspect and record a check for that version before inviting reviewers. The reviewer receives the separate file only; there is no fallback to the author file if it is missing. Neither the PDF nor the title, abstract or metadata is anonymised automatically: both author and editor must inspect them, and the check cannot guarantee anonymity.
- An authorised editor can record a reviewer invitation for the same journal. Before accepting, the reviewer must explicitly declare no conflict. The reviewer may instead report a conflict with a private explanation, including if one arises after accepting or submitting a report. Conflict declarations are retained as a history and shown to authorised editors, not authors; access to the review file is blocked after a conflict is reported. The editor must assess the disclosure; earlier decisions are not automatically reversed. There is no email notification.
- The assigned reviewer can accept or decline and can download only the file for that open review round after acceptance and a no-conflict declaration. An accepted reviewer can submit one confidential report per round. Authors do not automatically receive reports or reviewer identities.
- An editor can record a decision and a separate message to the author. Acceptance or a revision request requires at least one completed report with a current no-conflict declaration; desk rejection is allowed. The decision closes the round, preventing unfinished invitations and reports from being completed. The message is visible to the author, so the editor is responsible for keeping reviewer identities and confidential text out of it.
- Following a revision request, the author uploads a new PDF and response to the editor. The prior file, decision and reports remain recorded, and a new review round opens for the new version. Reviewers need a new invitation and acceptance for that round; previous access does not carry over. Former reviewers cannot act as editors on that manuscript, and recorded editors cannot be invited to review it in a later round.
- Authentication uses Django accounts and sessions; state changes use POST and CSRF protection. Role checks are enforced in server-side views. Privileged administrators do not automatically receive manuscript access through these views. A minimal event trail records the actor and action without storing manuscript or report text.
- PDF files are stored in `.runtime/private-media`, outside the static site, and downloaded only via an authorisation check. The development database is `.runtime/dev.sqlite3`. Both locations are ignored by Git. File checks limit the extension, basic header and size; they are not malware or content validation.
- The backend interface supports English and Simplified Chinese. Its separate static prototype retains the 12-language selector described in the root README.
- Local rule-based checks report whether required fields and test files are present. They do not use AI, verify scientific quality or establish that a file is safe.
- A default-off local publication simulation requires an assigned editor to start production and an eligible coordinator to assign a production editor for that manuscript. An assigned production editor can access the accepted source PDF and production files but cannot access confidential reviews or reviewer identities merely through the production role. They prepare public metadata and a separate fictional publication PDF. The submitting author confirms the exact metadata and proof; the assigned production editor can then explicitly publish a local test article. Metadata edits and new proofs require fresh confirmation. Public test pages are marked `noindex` and show only the chosen test metadata and proof, not reviews. Anyone who can access the server can access a published test article.
- A coordinator can create a fictional volume and issue for each journal. A production editor can select an unreleased issue of that same journal before test publication; the submitting author must reconfirm if the selection changes. An independent coordinator can release an issue after it contains at least one published test article and no unpublished assignments. A released issue has a local public table of contents; no article or issue is posted to an external site.
- A journal site manager can create a fictional, journal-specific website draft, privately preview six distinct sample templates, customise colours and layout settings, arrange page modules or request an AI-generated design blueprint, and explicitly publish a version locally. A published version contains its own copy of the display name and design text. Historical versions can be restored to the draft and then separately republished. This role alone grants no manuscript access.
- A separately assigned publisher portal manager can design a fictional organisation portal and explicitly choose up to 50 active journals from that organisation. Six visual samples are starting points for independently editable colours and layout settings. The manager can preview, publish a local snapshot and restore prior versions to the draft; the role does not grant manuscript or journal-site management access. The manager can organise up to 12 page modules with plain-text content and optional images. AI visual-design, module-arrangement, independent-page and page-block requests have separate, default-off publisher AI switches.
- Journal and publisher site managers can each upload, select and preview fictional hero and module images in their own local image library. Draft and published releases separately retain the image, alternative text, crop/contain choice and focus position. A published image is available only while used in the current local release's hero, visible modules, visible independent pages or their visible content blocks; a replacement remains private until separately published.

## Run locally

Requires Python 3.10–3.14 and Node.js 18+ for the separate static-prototype tests. From the repository root:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements.txt
cd backend
python manage.py migrate
python manage.py seed_demo
python manage.py runserver 127.0.0.1:8000
```

On Windows, use `python` if `python3` is unavailable and activate with `.venv\Scripts\activate`. Open <http://127.0.0.1:8000/>. The seed command creates a fictional SCIENTARA-inspired group, two fictional test journals and ten randomly named test accounts. It prints unique, randomly generated passwords once in the terminal. Keep those credentials private. Sign in as the test author, coordinator, editor, reviewer, production editor, site manager, journal AI manager, publisher portal manager and publisher AI manager in separate browser sessions to try each role; one additional account is an editor for the other journal. After the author submits, the coordinator opens **Manage editor assignments** and assigns the test editor. The test journals require two fictional PDF files; the editor must inspect the reviewer copy before inviting the reviewer. Running the command again creates a separate set of test records; it does not reset existing accounts.

For manual management of test organisations, journals, users and journal roles, run `python manage.py createsuperuser` and visit `/admin/`. The admin site does not register submission and review models; having an administrator account does not itself grant manuscript access in the workspace. A development secret is generated at each process start, so sessions end when the server restarts.

The upgrade from the initial local backend creates version and round records for existing test submissions and retains the original file paths and review assignments. Existing journals and submissions retain the standard-file policy; changing a journal's policy affects new submissions only. Older accepted or submitted review tasks have an unknown conflict declaration rather than a fabricated one. Their reviewer must record a no-conflict declaration before file access or a further report, and an undeclared completed report does not count towards an acceptance or revision decision. Migration 0005 does not infer editorial assignments: existing submissions remain unassigned until an administrator grants a journal coordinator role and the coordinator explicitly assigns eligible editors. Migration 0006 does not create or publish articles automatically. Migration 0007 does not infer production assignments: a coordinator must explicitly assign an eligible production editor to each existing production draft before staff can access it. Migration 0008 leaves existing articles without an issue and preserves existing confirmations; no issue is inferred or released. Migration 0009 does not create a journal site or grant the site manager role to existing accounts. Migration 0010 does not create an AI policy or grant an AI manager role: even if the old AI switch was enabled, the task is blocked until a policy is explicitly configured. Earlier AI results retain an unknown policy revision. Migration 0011 leaves the new AI site design option disabled for every existing policy. Migration 0012 preserves previous site drafts and published snapshots in their legacy appearance, and existing AI design suggestions remain viewable. Migration 0013 preserves those drafts, releases and existing AI suggestions without adding or changing page modules. Migration 0014 leaves the new module-arrangement AI switch disabled for every existing journal, even if visual design is enabled. Migration 0015 does not infer any organisation portal manager or create a portal; existing journal sites and AI policies remain unchanged. Migration 0016 creates no publisher AI policy and grants no publisher AI manager role, and preserves existing publisher portals and journal AI policies. Migration 0017 keeps all existing portal drafts, releases and visual-design requests in their prior form and leaves AI module arrangement disabled for existing publisher policies. Migration 0018 preserves earlier drafts, releases and AI suggestions without adding images or changing their fingerprints. Migration 0019 adds protected module-image references while retaining existing hero images, module text, snapshots and AI suggestions. Migration 0020 preserves those records and adds empty page lists to existing drafts and releases without changing their fingerprints. Migration 0021 preserves earlier pages and AI runs while leaving the new independent-page AI switches disabled. Migration 0022 preserves those records and leaves the new page-block AI switches disabled. The migrations are deliberately one-way so that a rollback cannot silently discard new versions, declarations, assignments, proofs or decisions. Back up the test database and files before upgrading; restoring a backup is the supported way to return to the earlier test version.

## Optional local publication simulation

Use fictional materials only. The feature is disabled by default and works only with the development `DEBUG` setting. To enable it while binding the development server to the local machine, run from `backend/`:

```sh
IPS_LOCAL_PUBLICATION_ENABLED=1 python manage.py runserver 127.0.0.1:8000
```

In Windows PowerShell, set `$env:IPS_LOCAL_PUBLICATION_ENABLED='1'` before running `python manage.py runserver 127.0.0.1:8000`. To disable it, stop the server, unset the variable, and restart. A `noindex` header is a request to search engines, not an access control; any person who can connect to the server can view published test pages and download their PDF. Do not expose this development server to the internet.

With the same option enabled, sign in as the site manager and open **Journal site design** in the workspace. Create a draft with fictional text, preview the sample templates and apply one to the draft. Independently adjust three hexadecimal colours, composition, typography, hero style and alignment, spacing, corners, section order and the feature panel, then save and preview it. The samples are starting points; custom colour and setting combinations are not restricted to them. In **Page modules**, add, edit, hide, delete and reorder up to 12 modules, including journal introduction, articles and issues, aims and scope, editorial board, editorial policies, author information, special issues, announcements, contact details and named custom sections. Module text is plain text and each module can use one image from the site library; the article archive module links to local test articles. The journal introduction module uses the saved introduction when its module text is left blank. Drag the handle with a pointer, use the move buttons, or enter order numbers; without JavaScript, the blank module and order numbers remain usable. Save changes before previewing. Once configured, module order takes precedence over the older appearance section-order setting; AI visual-design blueprints affect appearance only; the separate AI module-arrangement task can suggest module order, visibility and additional empty modules for review. Publishing requires two confirmations and makes that snapshot visible to anyone who can reach this test server. Later edits remain private until separately published. Restoring a historical version changes only the draft; review and publish it separately. Each site's manager must have the site-manager role in that journal. Interface labels support English and Simplified Chinese, but site text is a single manually entered version and is not automatically translated. The local site-image library is described below. Custom HTML, unrestricted freeform page editing and custom domains are not supported; this does not deploy to SCIENTARA or an external host.

With the same option enabled, sign in as the separate **publisher portal manager**, open **Publisher portal design**, create a fictional draft, select the journals to show, preview a sample or edit visual settings, and confirm local test publication. Selection is explicit, limited to active journals in the organisation and initially empty. Published journal names and text are frozen in the portal snapshot. Links appear only while each selected journal has its own valid local published site; disabled, moved or slug-changed journals are hidden. Restoring a version changes only the draft and requires its selected journals still to be available in the organisation; restored selections use current journal names in the draft and upon republication. The portal interface is in English and Simplified Chinese; content is entered manually. The portal manager can add, edit, hide, delete and reorder up to 12 modules, including a journal list, news, publishing services and custom plain-text sections. Drag handles, move buttons and numeric order fields are supported; module order takes precedence over the appearance section-order setting. The selected journal list is displayed only within a visible journal module. Existing unmodified portals keep their previous layout. Visual-design and module-arrangement AI suggestions are documented below. The local site-image library is described below. Unrestricted freeform layout and custom domains are not implemented yet.

After an assigned editor records acceptance for the latest version, the editor opens the submission and starts local production. A coordinator opens **Manage editor assignments**, selects the submission and then **Manage production assignments**, and assigns an eligible production editor. The production editor opens the task in their workspace, may download the accepted source PDF, enters fictional public author names and metadata, and uploads a separate fictional publication PDF. The submitting author signs in, downloads the current proof, and confirms the current metadata and PDF. The assigned production editor must explicitly confirm publication. Replacing the proof or changing metadata requires a new author confirmation. The system stores each test proof and checks its SHA-256 digest when confirming, publishing and downloading; the check is not virus scanning or a content review. Publication freezes the test record in this interface; correction, retraction and removal workflows are not implemented.

In the coordination workspace, choose **Manage test issues** for a journal to create an issue with volume, number, year and optional title. These details cannot be edited after creation. Before publishing an article, the assigned production editor may select an unreleased issue from the same journal or leave the article online first without an issue. The issue choice is included in the author's confirmation; any change needs a new confirmation. After article publication the choice cannot be changed, so an online-first test article cannot later be placed in an issue in this prototype. The article page is available locally as soon as the article is published, even before its issue is released.

An issue can be released only by a coordinator who is not the submitting author, an invited reviewer or a recused editor/production editor for any included article. These checks cannot identify other coauthors or all possible conflicts; a person must assess them. Release requires at least one published test article, no unpublished assignments and intact published test PDFs; released issues accept no new articles. The local issue page lists its published articles in test-publication order. Manual ordering, pagination, article numbers, subsequent issue edits and issue withdrawal are not implemented. `noindex` is not an access control; anyone who can reach the local server can read a published test article or a released issue.

A production editor requires both an active journal role and an active assignment for that draft. An author, any invited reviewer, a person who has recused from editorial or production work, and the assigning coordinator cannot be assigned. A production editor may recuse; this also blocks their editorial and coordinator access to that manuscript. Recusal as editor likewise blocks their production access. Removing an assignment blocks subsequent requests to the production workspace, accepted source and private proofs; a download already in progress cannot be recalled. If a test article was already published, its public page and PDF remain available to anyone who can reach the test server. Assignment history, previous decisions and author confirmations remain. A person can have both editing and production roles only when each role is separately assigned. These checks do not identify every possible conflict, and role assignment must be reviewed by humans.

The confirmation belongs only to the submitting account and does not establish that all coauthors, editors or rights holders approved publication. The simulation does not provide proof annotations, full issue editing and scheduling, licence management, DOI registration, indexing or formal publication. It is not evidence of publication and must never be used for real manuscripts.

## Independent site pages

Journal and publisher site managers can open **Manage independent pages** from the respective design workspace. Create up to 20 pages with a unique lowercase URL name, a custom title, plain-text body, optional site-library image and accessible description. Use order numbers for navigation and a visibility checkbox to keep a draft page private. Save one new blank form at a time, then preview saved draft pages. Pages can inherit the site design or use a page-specific layout, adjustable width, text alignment and freely entered hexadecimal background and accent colours. Open **Edit content blocks** on any saved page to add up to 20 ordered text, image-and-text, highlight, quotation or link blocks. Each block can contain text, one site-library image with its own description and display settings, and a link. Blocks can inherit the site style or use individually editable colours, width, text alignment, image placement, padding, corner radius and image gap. Six-digit background and accent colours can be typed or selected with the browser colour picker and are not restricted to the sample palettes; without JavaScript, enter the hexadecimal values directly. Text is automatically rendered black or white for contrast against the selected background. Narrow screens display the blocks at full width and stack images. Links must be HTTPS or a local site path; they are not fetched by the server. Drag, use the move buttons, or enter order numbers. Without JavaScript, add one empty block per save. Block visibility is independent of page visibility; a hidden page hides all its blocks. The page can optionally use a responsive 12-column grid with an adjustable gap and row alignment. Each block can occupy any 1–12 columns (blank means full width); blocks wrap in their saved order and stack on narrow screens. For example, widths 8 and 4 place a main area beside a sidebar. A block’s custom width percentage applies within its assigned grid area. Grid settings remain in the draft and are published only with the site. Disabling the grid retains individual widths for later use. Existing unconfigured pages keep their previous single-column appearance.

The visible page list and content are snapshotted with the whole website when the manager explicitly publishes the local test site. Hidden pages and hidden blocks are not public; their images cannot be accessed by public image URLs unless separately used by a visible block on a visible page, another visible page, a visible homepage module or the current hero. Drafts and historical releases protect referenced images from deletion; restoring a version changes only the draft. Renaming a page URL breaks existing links after republication; there are no automatic redirects. Changes to pages invalidate draft-bound AI suggestions. Existing homepage AI requests do not automatically send page titles, text, image identifiers or image bytes. The separately enabled independent-page task described below can suggest text and page-specific design. Page content currently has one manually entered language.

## Optional AI suggestions for independent pages

The journal AI manager or publisher AI manager must separately enable the default-off independent-page suggestion switch. The corresponding site manager saves a fictional page, selects it in **Manage independent pages**, enters a fictional brief of up to 800 characters, and separately confirms the request and fictional-only data. The request sends the entered brief, the site type and whether the page has a primary image. It does not automatically send the saved page title, body, content blocks, URL name, image identifier or bytes, site name, journal information or manuscripts. Do not enter personal information or real research in the brief. API use may incur charges; `store: false` is not a guarantee of zero provider retention. Generated options and the final edited applied option are stored in the local test database; the brief is stored only as a fingerprint, which is not anonymisation.

One to three validated suggestions can include a title, a plain-text body of up to 2,500 characters, a page-specific layout, width, alignment and freely chosen colours; after applying, the normal page editor can expand the body. The manager can edit a suggestion, privately preview the edited version and explicitly apply it to the draft. This replaces the selected draft page's title, body and design; its URL, visibility, primary image and content blocks remain. Publishing requires separate confirmation. The model is instructed to use placeholders rather than invent identifying or policy facts, but this cannot guarantee accuracy. A person must check every statement, including names, indexing, fees and policies. Generated text with common markup or web/email addresses is rejected; the manager can add verified addresses as escaped plain text while editing. This page-suggestion task does not perform automatic fact checking, image generation or unrestricted freeform layout. The separate page-block AI task is described below.

Page suggestions share the existing journal or publisher rolling limit and account limit; failures and cancellations count. Results are requester-specific and require the current site-manager role. The policy, role, model and draft are checked immediately before dispatch; a later change may not stop a request already being sent. A changed draft invalidates suggestions. API output and previews have only been tested with a mocked provider, not a live OpenAI account or visual browser review.

## Optional AI suggestions for page blocks

A journal or publisher AI manager must independently enable the default-off page-block suggestion switch; enabling page-level suggestions alone does not enable it. In the saved page's **Edit content blocks** view, the site manager enters a fictional brief and explicitly confirms both the transmission and fictional-only content. Only that brief, the site type, the count of available block slots and the requested design count are sent; the current page title, URL, blocks, text, links, image identifiers, image bytes, site names and manuscripts are not automatically sent. Do not put personal information or real research in the brief. API charges and provider retention may apply. The brief is retained only as a fingerprint, which is not anonymisation; suggestions and the applied reviewed blocks are stored in the local test database.

The manager can choose a maximum of one to six distinct sets per request in this prototype; the AI may return fewer. The AI can propose text, image-placeholder, highlight and quotation blocks with individual colours, width, image placement, alignment, spacing and corner radius. It does not generate images or links. Suggestions fit within the page's 20-block prototype limit, with up to 800 characters per generated block body. The manager can edit the text and visual settings, manually assign grid widths, reorder, hide or remove proposed blocks, privately preview the resulting page, return to the editor with those changes intact, and explicitly add the reviewed blocks to the draft. Existing blocks, images, page text and settings remain unchanged. After applying, the normal block editor can add site-library images and verified links or continue editing. Publishing remains separate. AI can misstate or invent facts; people must verify names, indexing, fees, policies and all other claims. No automatic factual verification is performed.

Each attempt shares the site's and account's existing 24-hour limits, including failed and cancelled requests. Results are requester-specific and bound to the current draft and manager role. Permissions, policy and draft are rechecked immediately before dispatch; a change during or after that final check may not stop a request in progress. The page-block suggestion task does not automatically choose grid widths or change the page grid; managers can set widths while reviewing a proposal or use the separately enabled layout task below. The v2 visual proposal format preserves access to earlier v1 proposals and existing blocks. Grid layout and widths use existing page JSON; no new database migration is required. This feature has only been tested with mocked API responses and has not received browser visual or real drag-and-drop testing.

## Optional AI suggestions for existing page layouts

A journal or publisher AI manager must independently enable the default-off page-layout switch. After saving at least one fictional block, the site manager may enter a fictional brief, select up to six options and confirm both the transmission and fictional-only use. The provider receives only the brief, site type, option count and each existing block's temporary ID, order, type, visibility, image presence and grid width. Hidden blocks are included as descriptors. Block and page text, names, links, image identifiers and image bytes are not automatically transmitted. The brief is stored only as a fingerprint; suggestions are stored in the test database. API charges and provider retention may apply.

Each validated option contains every existing block exactly once, including hidden blocks, and proposes a 12-column width, ordering, gap and row alignment. A manager can drag visible blocks in the live desktop sketch, use move buttons for any block, choose common width shortcuts or enter any width from 1 to 12 directly. Numeric ordering remains available without JavaScript. The manager can privately preview the page, return to editing and explicitly apply the reviewed preview to the draft; the signed preview expires after 24 hours. Text, images, links, styles and visibility are preserved. The resulting grid stacks on narrow screens; publishing remains separate. This is not a freeform canvas, image generator, factual verification service or production system.

The request uses the existing site and account limits, scoped roles and current draft fingerprint. A changed draft or AI policy invalidates the result; the policy and role are rechecked immediately before dispatch, although a later change may not stop an in-flight request. Invalid provider output is rejected. The end-to-end workflow has only been tested with mocked AI responses; no live OpenAI call has been verified.

## Local site-image library

With local publication enabled, a journal site manager or publisher portal manager can upload an entirely fictional, single-frame JPEG, PNG or WebP file, supply an accessible image description, choose crop-to-fill or fit-entire-image, and choose the focus position. Input files must be at most 5 MB, at most 4096 pixels per side and at most 12 million pixels; re-encoded files over 8 MB are rejected. The server decodes and re-encodes images to JPEG or PNG, applies EXIF orientation, and removes file metadata. This is not a malware scan or a production security review.

Each site has an isolated library of at most 50 images, stored in the local development database. Managers can select another image or update its description and display settings, clear the draft image, and delete an image that is not referenced by any draft or published version. Historical release references are protected. Private library and draft images require the site's manager role. A public test image is served only while selected in the current published snapshot, to anyone who can reach the local server. Every response checks the stored SHA-256 digest. A later draft change does not alter the published image; restoring a prior release affects the draft until republished. Changing an image or its settings invalidates earlier draft-bound AI suggestions. Existing AI requests do not automatically send image bytes or image descriptions.

Managers may upload an image to the library without changing the hero, then select one image per page module and enter its description, display mode and focus. Modules keep their images when reordered or when an AI arrangement is applied. Drafts and every published version protect their referenced images from deletion. A module, page or block image is publicly served only if it is used in a visible homepage module, visible page or visible block on a visible page in the current local release; a hero image remains public while selected as the current hero. AI arrangement requests do not automatically send image identifiers, descriptions or bytes. The prototype does not generate images with AI, support multiple images in one block or homepage module, or provide arbitrary page layouts. Independent pages can have multiple images by using multiple blocks. Use fictional data and keep the server local.

## Draft contributor details

Submitting authors may add, reorder or remove up to 100 fictional contributors before initial submission. The list supports names, affiliations, email addresses, optional ORCID iDs and multiple corresponding authors. When the list is nonempty, at least one corresponding author and an email for each corresponding author are required to submit. An empty list remains permitted for compatibility with existing drafts. ORCID syntax and the ISO 7064 MOD 11-2 check digit are checked locally ([ORCID identifier structure](https://support.orcid.org/hc/en-us/articles/360006897674-Structure-of-the-ORCID-Identifier)); no registry lookup, identity verification or consent collection occurs. Coauthors do not gain accounts or manuscript access. The submitting author and the assigned editor can see the list; the review-task page does not display it, although manuscript files, titles and abstracts may still contain identifying information. The list is not copied to production or automatically checked for conflicts. Use only fictional data in this prototype.

After initial submission and before the final editorial decision, the submitting author can request a change with a reason and a complete proposed author list. Only one pending request is allowed. The submitting author or an assigned editor may upload up to 50 fictional evidence PDFs per request (maximum 5 MB each). Uploaders can access their own files; assigned editors can access all request files. These files are outside public media routes, have random stored names, and are checked against a SHA-256 digest before download and approval. The PDF header and digest checks are not a malware scan or proof of identity, authenticity or consent. Evidence should be protected and retained according to an appropriate policy in any eventual production system.

An assigned editor sees the before/after lists and records a separate manual check for each entry in both snapshots, citing an uploaded file for each confirmed entry. A file can support multiple entries, but no identity matching is inferred. Checks are stored as a history; disputes, missing checks and unavailable or changed evidence prevent approval. The editor must additionally attest that potential conflicts were assessed. An author may withdraw a pending request. A pending request blocks editorial decisions; a stale or finalised submission cannot be approved. A decision applies the new list only once and retains the snapshots and actor/time records. Previously approved requests are not retroactively represented as having evidence checks. Changes after acceptance, rejection or publication require a separate workflow that is not implemented.

Optionally, the assigned editor can map each original or proposed author entry to an existing active author account in that journal and attest that the mapping was checked manually. The account holder sees the reason and both name lists in a separate workspace task, but receives no email and gains no manuscript, review or evidence-file access. The account can agree or disagree and change its response while the request remains open; the response and its history are bound to the displayed snapshots and reason. Once closed, the recipient and assigned editors can review their permitted history in read-only form while retaining access; the workspace shows at most the latest 50 tasks and the response page at most the latest 50 responses. Unanswered or disagreeing account tasks, or a respondent who no longer has an eligible active author account, block approval; a pending task may be cancelled with a recorded reason, while an answered task cannot be cancelled. A new agreement is unavailable after the 30-day deadline, but disagreement remains possible. Each account can be assigned to at most one entry per list, and any account ever assigned a response task is excluded from reviewer, editor, coordinator and production roles for that manuscript. These checks do not establish that an account is actually owned by the named person. Account replies do not replace the mandatory manual evidence checks, and no author responses or evidence are automatically sent to AI. Use only fictional information; do not treat this prototype as a production authorship-consent system.

## Journal AI policy for local testing

A journal AI manager can open **Journal AI policy** in the workspace and independently enable the title-and-abstract task, visual design, module arrangement, independent-page, page-block and page-layout suggestions. Existing visual-design permission does not enable module arrangement. For metadata, the policy chooses whether submitting authors and assigned editors may request it; a journal administrator must also enable **Allow OpenAI metadata suggestions** in `/admin/`, and submitting-author consent for the exact metadata and per-request confirmation are required. Site design instead requires an authorised journal site manager and per-request confirmation; it does not use the metadata administrator switch. These tasks are disabled until explicitly enabled, require server configuration, and share a journal-wide rolling 24-hour limit between 1 and 100. The AI manager role alone does not grant access to manuscripts, abstracts or review reports. Policy history records configuration changes and actor, not manuscript text or keys.

Each journal counts attempts from its AI tasks over the preceding 24 hours, including failed and cancelled requests; the three-per-account limit shared with publisher portal AI design also applies.
